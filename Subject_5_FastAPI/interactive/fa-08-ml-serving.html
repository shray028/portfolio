Serving an ML model

The course's second project: an Insurance Premium Category predictor. A classifier pickled to model.pkl predicts Low / Medium / High. Users type raw facts; the model was trained on engineered features. The API's job is to bridge that gap — reliably, for every request.

Concept

The client sends what a human knows; the schema derives what the model needs Must-know

UserInput validates the raw fields and turns them into model features with @computed_fields: bmi from weight and height, age_group from age, lifestyle_risk from smoker and BMI, city_tier from the city. Doing this in Pydantic means it's validated, documented, unit-testable and identical for every request — no training/serving skew.

Concept

Streamlit → FastAPI → UserInput → model → JSON

The Streamlit form posts JSON. FastAPI matches POST /predict, Pydantic validates and computes features, predict_output builds a one-row DataFrame (sklearn pipelines expect named columns) and calls predict and predict_proba, and the response carries the category, the confidence and every class probability.

Concept

Never unpickle per request Must-know

Loading inside the endpoint re-reads and unpickles the file for every request: hundreds of milliseconds of wasted latency, disk I/O and memory churn. Load once at start-up — at module level (the course) or, better, in the lifespan handler — and every request reuses the in-memory object.
