async def vs def

The most-asked FastAPI question the playlist doesn't cover. FastAPI runs async def endpoints directly on a single event loop and plain def endpoints in a thread pool. Put one blocking call in the wrong place and every user waits.

2 sectionsEvent-loop simulator · async-or-def drill
Concept

async def → runs on the event loop Must-know

One thread juggles every request. It only switches to another request at an await. A blocking call — time.sleep, requests.get, a heavy model.predict — holds the loop, so nothing else runs, not even /health.

def → runs in a thread pool

FastAPI hands plain def endpoints to a worker thread pool (40 threads by default, via AnyIO), so blocking code is safe and the loop stays free. The cost is a little thread overhead and a cap on how many run at once.

The decision rule

Using an async library (httpx.AsyncClient, asyncpg, Motor, aiofiles)? → async def and await it. Using sync libraries or CPU work (pandas, scikit-learn, requests, a sync DB driver)? → plain def. Heavy CPU at scale? → more worker processes (--workers N), a task queue (Celery / RQ) or a dedicated model server. Threads don't add CPU parallelism for pure-Python code because of the GIL; NumPy and most sklearn internals release it for chunks of work.
