1 Source Document
Ingest & Parse — What it is & why it helps
  • The “extract content” step does more work than it looks — PDFs are messy: multi-column layouts, tables, embedded images, scanned pages.
  • Tooling: PyMuPDF (fast free text), Docling (layout-aware, tables → clean Markdown), LlamaParse (messy tables / scanned, API), Unstructured.io (docx, pptx, html, email), Azure Doc Intelligence / AWS Textract (OCR for scanned & enterprise docs).
  • Structured XML (e.g. ARXML): a purpose-built two-pass streaming parser with an in-memory object model beats any generic loader — it lets you navigate, edit and re-serialize the model, which chunk-and-embed loaders can’t.
  • Why it helps you: clean parsing = better answers downstream; a custom parser turns hours of manual doc digging into minutes.
Things to be careful of
  • Scale pain: naive per-file synchronous parsing becomes the bottleneck — move parsing to a queued / parallel batch job, not an inline step.
  • Mistake: one generic parser for every file type — scanned PDFs silently return empty or garbled text if OCR isn’t triggered, and nobody notices until retrieval quality drops.
  • Mistake: throwing away structure (headers, tables, XML hierarchy) at parse time — far more expensive to reconstruct later.
  • Scale pain: re-ingesting the entire corpus on every update instead of diffing / incrementally updating only changed documents.

2 Text Chunking
Chunking — What it is & why it helps
  • The step most RAG systems get lazy about, yet usually the biggest single lever on retrieval quality.
  • Fixed-size: split every N tokens with overlap — baseline only, breaks semantic units.
  • Recursive character splitting: try paragraph → sentence → word boundaries in order (RecursiveCharacterTextSplitter) — solid default for prose.
  • Semantic chunking: embed sentences, split where cosine similarity between consecutive sentences drops — better topic coherence.
  • Structure-aware: split by headers, XML elements or code functions — best for structured docs like ARXML.
  • Agentic / LLM-based: an LLM picks split points by meaning — highest quality, highest cost.
  • Contextual retrieval: prepend a short LLM summary of surrounding context to each chunk before embedding — fixes the “chunk loses meaning out of context” problem. Newer models (e.g. Voyage contextual embeddings) push this into the embedder itself.
Things to be careful of
  • Scale pain: a single fixed chunk size rarely fits both short FAQ-style content and long technical sections — one-size-fits-all chunking hurts recall as the corpus diversifies.
  • Mistake: chunking without overlap — cuts sentences and references in half at boundaries and silently drops context.
  • Mistake: re-chunking the whole corpus from scratch whenever the strategy changes, instead of versioning strategies so old and new can be compared.
  • Scale pain: chunk count grows faster than document count with recursive splitting — index size and embedding cost scale non-linearly if chunk size isn’t revisited.

The document is split into smaller, meaningful pieces called chunks. Think of it like cutting a long story into paragraphs — each chunk should contain one complete idea.

3 Generate Embeddings
Embeddings — What it is & why it helps
  • A cheaper embedder + a reranker often beats an expensive embedder alone, at lower total cost — worth remembering before over-optimizing this step in isolation.
  • Open source: BGE-M3 (2026 default, 100+ languages, pairs with BGE-reranker-v2), Qwen3-Embedding-8B (tops multilingual MTEB, self-hostable), nomic-embed-text (lightweight, laptop / edge via Ollama).
  • API: Voyage-3-large / voyage-context-4 (best for code & technical docs), Cohere Embed v4 (text + images, 128K context), OpenAI text-embedding-3-large (widest SDK support).
  • Non-negotiable: whatever model embeds the documents must also embed the query — same model, same vector space.
Things to be careful of
  • Scale pain: embedding cost & latency scale linearly with corpus size — re-embedding everything on every model upgrade gets expensive; batch and cache early.
  • Mistake: mixing vectors from two different models (or versions) in the same index — similarity scores become meaningless across the mismatch.
  • Mistake: not tracking which model / version produced which vectors, making later migrations error-prone.
  • Scale pain: dimensionality drives memory — a jump from 384-dim to 1536-dim can multiply storage 4× at large scale.

Each chunk is converted into a list of numbers (a vector) by an Embedding Model. Words with similar meanings get similar numbers — this is how the computer "understands" language.

4 Store in Vector Database
Vector DB / Semantic Index — What it is & why it helps
  • The field has fragmented by use case rather than one clear winner — pick by workload.
  • FAISS — library, not a DB; fast local prototyping, no persistence / metadata layer.
  • ChromaDB — great developer experience; fine up to a few million vectors.
  • Qdrant — Rust, self-hosted; 10–25% faster on common workloads, strongest filtered search.
  • Weaviate — bakes embedding generation into the DB, strong built-in hybrid search.
  • Milvus / Zilliz — distributed, built for billion-scale similarity search.
  • pgvector — right default for ~70% of workloads under 10M vectors when already on Postgres; metadata filtering comes “free” via SQL joins.
Things to be careful of
  • Scale pain: flat / exact-search indexes (e.g. plain FAISS IndexFlatL2) stop being viable past millions of vectors — approximate indexes (HNSW, IVF) trade a small recall hit for large speed gains.
  • Mistake: not planning metadata filtering early (date, source, permissions) — bolting on filters after the index is built is far more painful.
  • Mistake: single-node Chroma / FAISS with no persistence or replication story — a hard wall once uptime or horizontal scale matters.
  • Scale pain: index rebuild time grows with corpus size — full re-indexing on every update is fine at 10K docs, painful at 10M.

The embeddings are stored in a Vector Database (like Pinecone, FAISS, or ChromaDB). Each entry stores both the embedding numbers AND the original text chunk — so we can retrieve the text later.

Phase 2 — Retrieval & Generation
5 User Asks a Question
Semantic Search — What it is & why it helps
  • Pure vector similarity alone underperforms in production. The trending default is hybrid search.
  • Dense retrieval (embeddings) catches semantic / paraphrase matches.
  • Sparse retrieval (BM25 / keyword) catches exact terms — critical when domain terms (e.g. ECU / ARXML element names) are exact-match and embeddings alone miss them.
  • Reciprocal Rank Fusion (RRF) merges both ranked lists without needing to normalize scores.
  • Query rewriting / HyDE: have an LLM rewrite a vague query into a retrieval-friendly form, or generate a hypothetical answer and embed that instead of the raw question.
Things to be careful of
  • Mistake: relying on dense retrieval alone and skipping BM25 / keyword matching, which quietly fails on exact identifiers, part numbers or domain jargon.
  • Mistake: fixed top-k regardless of query type — a specific factual query and a broad exploratory query need different k, but most pipelines hardcode one value.
  • Scale pain: top-k retrieval returns many near-duplicate chunks as the corpus grows, crowding out distinct results — diversity-aware retrieval (MMR) becomes necessary.
  • Scale pain: query latency creeps up as both dense and sparse indexes grow; fusing two large ranked lists per query becomes a real cost at high volume.

6 Embed the Query
Query Embedding — What it is & why it helps
  • The question is embedded with the exact same model and vector space as the documents — this is what makes numbers comparable to numbers.
  • This step is the bridge between ingestion and retrieval: the same embedding stage from Step 3, now applied live to the user’s question.
  • Cheap to cache — identical or repeated queries can reuse their embedding instead of re-computing it.
Things to be careful of
  • Mistake: embedding the query with a different model or version than the documents — similarity scores become meaningless.
  • Mistake: forgetting to apply the same preprocessing / normalization at query time that was used at ingest time.

The question is also converted to an embedding — the same way the document chunks were. Now we can compare numbers to numbers!

7 Cosine Similarity Search
Similarity + Reranking — What it is & why it helps
  • Cosine similarity ranks first-stage candidates by the angle between vectors: 0 = unrelated, 1 = identical meaning.
  • Reranking is the single highest-leverage, lowest-effort fix in most RAG systems — it re-scores the top-N candidates with a cross-encoder that reads query and chunk together.
  • BGE-reranker-v2-m3 (open source, multilingual, default self-hosted), Cohere Rerank 3.5 / 4 (API, via Bedrock), ColBERTv2 (late-interaction, token-level scoring).
  • Impact: rerankers typically lift ranking quality by 5–15 points (NDCG@10), 20+ on lexically hard data, for under 200ms of added latency.
Things to be careful of
  • Scale pain: reranking every retrieved candidate (rather than a bounded top-N) becomes a latency bottleneck — reranker cost grows with candidates × queries, not just corpus size.
  • Mistake: skipping reranking to save latency, then trying to fix poor answer quality at the generation stage instead — usually the wrong layer to fix it at.
  • Mistake: using a reranker trained on general web data for a narrow technical domain without validating it actually improves ordering on that domain’s queries.

We compare the query embedding against every chunk embedding in the database. Cosine similarity measures the angle between two vectors — closer angle = more similar meaning!

📐 Cosine Similarity Formula

similarity(A, B) = A · B‖A‖ × ‖B‖
🔹 A · B = dot product (multiply matching numbers, sum them up)
🔹 ‖A‖ = magnitude (length) of vector A
🔹 Result ranges from 0 (unrelated) to 1 (identical meaning)

8 LLM Generates Answer
Generation (LLM) — What it is & why it helps
  • Implementation details matter more than model choice alone:
  • Context assembly: order matters — put the most relevant chunk closest to the question, not buried in the middle (models attend less to the middle of long contexts).
  • Citation grounding: instruct the model to cite chunk IDs, then post-verify the citation actually supports the claim.
  • Fallback handling: explicitly tell it to say “not found in context” rather than hallucinate when retrieval returns nothing relevant.
  • Local vs API: local models (e.g. via Ollama) keep data on-prem — important for internal engineering docs; hosted models (e.g. via Bedrock) give stronger reasoning for agentic RAG.
Things to be careful of
  • Scale pain: stuffing more chunks into context to improve recall raises cost & latency and can drop quality from “lost in the middle” effects — bigger context isn’t a free win.
  • Mistake: no citation verification step, so the model cites a chunk ID that doesn’t support the claim — erodes trust quietly since it looks grounded.
  • Mistake: no fallback instruction for empty / weak retrieval, so the model hallucinates a plausible answer instead of saying it doesn’t know.
  • Scale pain: generation is usually the most expensive stage per query — uncontrolled context length is the single biggest cost driver in the whole pipeline.

The best matching chunk is sent to the LLM as context along with the original question. The LLM reads the context and generates a grounded, accurate answer — no hallucination!

9 Final Answer
Why RAG Matters + Orchestration
  • Why RAG helps your tasks: it grounds answers in your own documents (no hallucination), keeps knowledge current without retraining the model, cites its sources, and turns days of manual doc digging into minutes.
  • The whole pipeline is wrapped by an orchestration layer: LangChain (broad integrations, chains), LlamaIndex (retrieval-first, best-in-class ingestion / indexing), LangGraph (agentic, cyclical retrieve → grade → rewrite → re-retrieve), DSPy (prompt optimization), Haystack (modular).
  • The pattern most teams settle on: LlamaIndex for retrieval + LangChain / LangGraph for orchestration + RAGAS for eval.
  • Next step / differentiator: frame it as an agentic LangGraph loop; consider GraphRAG (retrieval over a knowledge / entity graph) for structured domains like ARXML.
Things to be careful of
  • Scale pain: linear chains that worked in prototyping break once real queries need retries, branching or re-retrieval — the move to a graph / cyclical orchestration usually happens later than it should.
  • Mistake: no evaluation harness (e.g. RAGAS) before scaling traffic, so regressions from a chunking, embedding or prompt change go unnoticed until users complain.
  • Mistake: tightly coupling orchestration logic to one vector DB or one LLM provider, making later swaps expensive.
  • Note: tooling reflects the mid-2026 landscape — re-verify against vendor docs before committing to a stack.

The LLM produces a natural language response, grounded in the retrieved context. The user gets an accurate answer — that's RAG in action!
