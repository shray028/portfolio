MODULE 09 · RAG

RAG fundamentals

Retrieval-Augmented Generation: fetch the right pieces of your own data at question time and give them to the LLM as context, so answers are current, private-data-aware and citable. Most RAG interview questions are really about the retrieval half — how you chunk, embed, search and re-rank.

Concept

Index once (offline), retrieve and generate per question (online) Must-know

Indexing: load documents → clean and parse (tables, headings) → split into chunks → embed each chunk → store vectors with text and metadata (source, date, access rights) in a vector index. Query time: optionally rewrite the question → embed it → retrieve top-k chunks (dense, keyword or hybrid, with metadata filters) → re-rank → build a prompt with the chunks and instructions to answer only from them and cite → generate → return answer with citations. LLMs alone are frozen at their training cut-off, don't know your private data and can't show sources; RAG fixes all three without retraining.

Chunk size is a precision–context trade-off Must-know

Too small: chunks lose context ("it", "the above"), answers get split across boundaries, and you need more of them. Too large: the embedding averages several topics so similarity gets fuzzy, irrelevant text dilutes the prompt, and fewer chunks fit in context. Typical starting points are 256–1024 tokens with 10–20% overlap so sentences at boundaries appear in both neighbours. Prefer structure-aware splitting (headings, paragraphs, sentences — "recursive" splitting) over fixed character counts, keep tables intact, attach metadata, and tune size on a retrieval eval set rather than guessing.

Concept

Embeddings place meaning in space; cosine similarity measures the angle Must-know

\( \cos(q,d)=\frac{q\cdot d}{\lVert q\rVert\,\lVert d\rVert} \)

An embedding model (usually a transformer encoder trained contrastively on query–passage pairs) maps text to a vector of a few hundred to a few thousand dimensions, so that texts with similar meaning are close — "get my money back" lands near "refund". Cosine similarity ignores vector length and compares direction; for unit-normalised vectors it equals the dot product and ranks the same as Euclidean distance. Query and documents must use the same embedding model (re-embed everything if you change it). Exact search is O(n); vector databases use approximate nearest-neighbour indexes (HNSW graphs, IVF clusters, product quantisation) to search millions of vectors in milliseconds at slightly lower recall.

Concept

Keyword search finds exact terms, dense search finds meaning — hybrid gets both Must-know

BM25 (sparse) scores documents by matching terms, weighting rare terms (IDF) and saturating repeated ones; it nails error codes, product SKUs, names and acronyms, and needs no training — but misses synonyms. Dense retrieval matches paraphrases and intent but can miss exact identifiers and rare jargon. Hybrid runs both and fuses the ranked lists, commonly with Reciprocal Rank Fusion, which needs no score normalisation:

\( \text{RRF}(d)=\sum_{r\in\text{rankers}} \frac{1}{k+\text{rank}_r(d)},\quad k\approx 60 \)

Concept

Retrieve wide and cheap, then re-rank narrow and precise Must-know

A bi-encoder embeds query and document separately, so document vectors are pre-computed and search is fast — but the two texts never "see" each other. A cross-encoder reads the query and a document together through full attention and outputs a relevance score: far more accurate, far too slow to run on millions of documents. So retrieve the top 20–100 candidates with hybrid search (high recall), re-rank them with a cross-encoder (or an LLM re-ranker), and send only the top 3–8 to the LLM (high precision, fewer tokens, less "lost in the middle").
