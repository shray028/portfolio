Agents & LLMOps

An agent is an LLM in a loop that can call tools. Interviews probe how the loop works, how tool calls fail, how to stop a document from hijacking the agent, and how to run all of it fast and cheaply enough to put in front of real users.

Concept

Reason → act → observe, until done Must-know

ReAct interleaves reasoning with actions: the model decides what it needs, calls a tool (search, SQL, calculator, an API), reads the observation, and repeats until it can answer. It beats reasoning alone because facts come from tools rather than memory, and it beats a fixed pipeline on open-ended tasks. The cost: more LLM calls, compounding errors, loops — so cap steps and budget, validate tool inputs/outputs, log every step, and prefer a fixed workflow when the steps are known in advance.

Concept

The model never runs the tool — your code does Must-know

You describe tools with a name, a description and a JSON schema. The model replies with a structured tool call (name + arguments). Your application validates the arguments, executes the function with the user's permissions, and sends the result back as a tool message; the model continues. Structured outputs use the same schema machinery to force a JSON answer with no side effects. MCP (Model Context Protocol) standardises how tool servers expose tools and data, so any compatible client can use them without custom glue.

Concept

Anything the model reads can try to give it orders Must-know

Direct prompt injection comes from the user ("ignore your instructions…"). Indirect injection hides in data the agent processes — a web page, an email, a PDF, a tool result. No single defence is complete, so layer them: separate trusted instructions from untrusted data, give tools least privilege, require human confirmation for consequential actions, filter inputs and outputs, and monitor. The model's obedience is not a security boundary; permissions are.

Concept

Cost and latency are mostly about tokens Must-know

Latency ≈ time-to-first-token (queueing + reading the prompt) + output tokens ÷ generation speed — so long answers are slow and streaming hides most of it. Cost ≈ input tokens × input price + output tokens × output price, per request. Levers: shorter prompts and fewer retrieved chunks, capped output length, prompt caching of stable prefixes, semantic caching of repeated questions, routing easy requests to a small model, batching offline work, and quantised or distilled self-hosted models at high volume.
