Design review — how I'd harden this architectureSuggestions beyond the exam answer

  1. Prefer an orchestrator over a long synchronous chain. A Prediction Orchestrator (behind the gateway) calling Validation → Preprocessing → Inference → Risk in turn keeps each service independent; in a pure chain every hop adds latency and one slow service blocks the rest.
  2. Timeouts, retries with back-off and circuit breakers on every synchronous hop, with a safe fallback response (“prediction unavailable — use clinical judgement”) instead of a hanging request.
  3. Transactional outbox: write the prediction and the outgoing risk.high event in the same DB transaction and relay it to Kafka, so an alert is never lost (or sent for a prediction that was never saved).
  4. Idempotency: the gateway's X-Request-ID doubles as an idempotency key; consumers de-duplicate so a redelivered risk.high doesn't page the team twice. Failed messages go to a dead-letter queue.
  5. Minimise patient data (PHI): replace the name with a pseudonymous patientRef before the ML path — inference never needs a name. Encrypt in transit (mTLS) and at rest; enforce RBAC at the gateway.
  6. Alert acknowledgement & escalation: Notification tracks whether a clinician acknowledged the alert and escalates if not — delivery alone isn't enough.
  7. Model monitoring & feedback loop: add a model-monitoring service for data/concept drift and calibration, fed by real outcomes, to trigger retraining and registry promotion.
  8. Observability via telemetry pipelines: metrics are usually scraped (Prometheus) or pushed through an OpenTelemetry collector rather than sent over Kafka; logs are shipped by agents.
  9. Append-only audit store (write-once, tamper-evident) to meet compliance requirements.
  10. Human in the loop: the score supports — not replaces — clinical decisions; show the top contributing vitals alongside the score.
Architecture summary

The hospital application sends patient demographics and vital signs through an API Gateway. The gateway routes the request through patient intake, validation and preprocessing services. The ML Inference Service retrieves the approved model and generates a deterioration probability. The Risk Scoring Service converts this probability into a risk level, persists the prediction, and returns the result synchronously to the hospital application.

Events generated throughout the flow are published asynchronously to Kafka. Notification, audit and logging components consume relevant events independently, and monitoring collects telemetry, ensuring that non-critical background work does not delay the patient prediction response. Redis provides low-latency temporary data access, while databases maintain durable patient, prediction and audit records.
