The scenario

A hospital wants an early-warning system: a clinician enters a patient's vitals and immediately gets a deterioration risk score. When risk is high the care team is alerted, and every request, prediction and alert is recorded for audit and monitoring.

Key design idea: the gateway routes, the Prediction Service orchestrates a synchronous workflow because a clinician is waiting, and alerts, audit and logs happen asynchronously so they never slow that answer down.

  • One front door that routes each APIAPI Gateway
  • Capture & validate patient vitalsPatient Service
  • Turn vitals into a risk scorePrediction Service → Feature · Inference
  • Alert the care team on high riskKafka → Notification
  • Record everything for audit & monitoringAudit · Logging · Monitoring

Why an orchestrator instead of a call chain?Gateway routes · orchestrator coordinates

ANTI-PATTERN · SYNC CALL CHAIN
Gateway→Intake→Validation→Preprocessing→Inference→Risk
  • The gateway has nothing to route — every request goes to the same first service.
  • Each service knows who comes next: tight coupling dressed up as decoupling.
  • Five nested hops: a timeout anywhere unwinds the whole stack.
  • Too fine-grained: nobody deploys or scales “Validation” on its own.
THIS DESIGN · ROUTE + ORCHESTRATE
Gateway→Prediction Service→Patient · Feature · Inference
  • The gateway routes four APIs to four owners: /patients, /predictions, /alerts, /audit.
  • One service owns the workflow; the others never call each other.
  • Timeouts, retries and fallbacks (e.g. cached features) live in one place.
  • Validation is a step inside Patient Service — pipe-and-filter belongs inside a service, not across service boundaries.

Honest caveat: the request still depends on every service it calls (≈ 0.99⁵ if each is 99% available) — the fallbacks are what actually improve availability.

Design review — how I'd harden this architectureWhat I'd add before running this in production

  1. Timeouts, retries with back-off and circuit breakers on every synchronous hop, with a safe fallback response (“prediction unavailable — use clinical judgement”) instead of a hanging request.
  2. Transactional outbox: write the prediction and the outgoing risk.high event in the same DB transaction and relay it to Kafka, so an alert is never lost (or sent for a prediction that was never saved).
  3. Idempotency: the gateway's X-Request-ID doubles as an idempotency key; consumers de-duplicate so a redelivered risk.high doesn't page the team twice. Failed messages go to a dead-letter queue.
  4. Minimise patient data (PHI): replace the name with a pseudonymous patientRef before the ML path — inference never needs a name. Encrypt in transit (mTLS) and at rest; enforce RBAC at the gateway.
  5. Escalation policy: the demo shows acknowledgement via /alerts; in production, unacknowledged alerts should escalate to the next on-call clinician after a few minutes.
  6. Model monitoring & feedback loop: add a model-monitoring service for data/concept drift and calibration, fed by real outcomes, to trigger retraining and registry promotion.
  7. Observability via telemetry pipelines: metrics are usually scraped (Prometheus) or pushed through an OpenTelemetry collector rather than sent over Kafka; logs are shipped by agents.
  8. Append-only audit store (write-once, tamper-evident) to meet compliance requirements.
  9. Human in the loop: the score supports — not replaces — clinical decisions; show the top contributing vitals alongside the score.
Architecture summary

The hospital application calls an API Gateway, which authenticates requests and routes each API to the service that owns it: /patients to the Patient Service, /predictions to the Prediction Service, /alerts to the Notification Service and /audit to the Audit Service. For a prediction, the Prediction Service orchestrates the workflow over gRPC: the Patient Service validates and stores the vitals, the Feature Service builds model features (cached in Redis), and the ML Inference Service scores them with the approved model from the Model Registry. The Prediction Service then applies the risk thresholds, persists the result and returns it synchronously.

Events generated throughout the flow are published asynchronously to Kafka. Notification, audit and logging components consume relevant events independently, and monitoring collects telemetry, ensuring that non-critical background work does not delay the patient prediction response. Redis provides low-latency temporary data access, while databases maintain durable patient, prediction and audit records.
